# 05 — التشغيل اليومي واستكشاف الأعطال

كل الأوامر على السيرفر كـ root من مجلد النشر:

```bash
cd /srv/repeater/app/deploy
alias dc='docker compose --env-file .env'      # اختصار للجلسة الحالية
```

## الحالة والسجلات

| المطلوب | الأمر |
|---|---|
| حالة الخدمات وسلامتها | `dc ps` |
| سجلات حية | `dc logs -f --tail 200 web worker` |
| أخطاء العامل فقط (سطور JSON) | `dc logs --no-color worker \| grep '"level": "error"'` |
| سجل Caddy (الشهادات) | `dc logs --tail 100 caddy` |
| فحص السلامة | `curl -s http://127.0.0.1:8090/healthz` (المنفذ من `REPEATER_WEB_PORT`) |
| فحص الإعدادات | `dc exec web python -m repeater.cli check` |
| الموارد | `docker stats --no-stream` |
| المساحة | `df -h /srv && du -sh /srv/repeater/media /srv/repeater/backups` |
| سجل النسخ الاحتياطي | `journalctl -t repeater-backup --since yesterday` |
| عمر آخر نسخة ناجحة | `bash backup.sh status` (يخرج بـ 1 لو مرّت 36 ساعة) |

السجلات تُدوَّر تلقائيًا (10 ميجا × 5 ملفات لكل خدمة). بدون SSH: **Actions ← Server inspect** يطبع آخر 100 سطر من web وworker.

## إعادة التشغيل والتحديث

- إعادة تشغيل اللوحة والعامل: `dc restart web worker`
- نشر الكود الحالي من جديد: `bash deploy.sh`
- تحديث عادي: ادفع إلى `main` (أو **Actions ← Deploy ← Run workflow**).
- بعد تعديل `deploy/.env` يدويًا: `bash deploy.sh` (يعيد إنشاء الحاويات التي تغيرت إعداداتها).
- العامل يُكمل المهام الجارية (ترميز أو رفع) قبل أن يتوقف: ينتظرها حتى `REPEATER_WORKER_SHUTDOWN_GRACE_S` (600 ثانية افتراضيًا) ثم يمنحه دوكر دقيقة إضافية قبل `SIGKILL` (`stop_grace_period` = القيمة + 60 ثانية). الترميز المقتول وسط العمل يُعاد من الصفر بعد انتهاء عقد المهمة، والنشر المقتول يتحول بعد ساعتين إلى "يحتاج مراجعة"، لذلك لا تقصّر هذه المهلة. بعد تغيير القيمة في `.env` شغّل `bash deploy.sh` (هو من يمرّر الجمع إلى compose؛ أمر `dc up` المباشر يستخدم القيمة الافتراضية 660 ثانية).
- النشر (`deploy.sh`) يأخذ قبل الترحيلات نسخة `repeater-predeploy-*` للقاعدة (آخر 5)، ولا يكمل بدونها.

## تحديث yt-dlp وصور الأساس

- yt-dlp يتحدث تلقائيًا مع **أول نشر في كل يوم** (طبقة مستقلة في الصورة تُعاد بناؤها فقط).
- تحديثه الآن (مثلًا بعد عطل في تيكتوك/يوتيوب): `bash deploy.sh --refresh-ytdlp`
- تحديث صور الأساس (Python، Postgres، Caddy) لإصلاحات أمنية، مرة شهريًا: `bash deploy.sh --pull`. يعيد بناء صورة التطبيق على أحدث Python، **ويسحب أيضًا** `postgres:16-alpine` و`caddy` (لو مفعّل)؛ الصورتان بلا قسم بناء، وبدون هذا الأمر يبقى كل منهما على أول نسخة سُحبت. حاوية القاعدة تُعاد إنشاؤها إن تغيرت صورتها (انقطاع قصير).
- الصورة تتضمن Deno لأن yt-dlp يحتاج محرك JavaScript لتنزيلات يوتيوب.

## الرجوع للإصدار السابق

كل بناء جديد يُسجَّل بوسمين على الصورة: `repeater-app:previous` (الإصدار السابق) و`repeater-app:build-<الوقت>` (آخر 4 إصدارات). **`previous` لا يتحرك إلا حين ينتج البناء صورة مختلفة فعلًا**: إعادة تشغيل Deploy (إعادة محاولة، تحديث مفاتيح، دفعة وثائق فقط) تبني الصورة نفسها من الكاش ولا تمسّ `previous`. السكربت يطبع أمر الرجوع في نهاية كل نشر.

```bash
REPEATER_IMAGE_TAG=previous bash deploy.sh --no-build     # أو build-<الوقت> لإصدار أقدم
```

**لو أضاف الإصدار الجديد ترحيلًا للقاعدة** فالإصدار القديم لا يعرف بنيتها الجديدة (يفشل `migrate` بأن النسخة غير معروفة)؛ الحل نسخة `repeater-predeploy-*` التي أخذها `deploy.sh` قبل ذلك الترحيل مباشرة، مع الوسم نفسه:

```bash
ls -t /srv/repeater/backups/repeater-predeploy-* | head -3
REPEATER_IMAGE_TAG=previous bash backup.sh restore /srv/repeater/backups/repeater-predeploy-<الوقت>.sql.gz --yes
```

الاسترجاع يمسح مخطط القاعدة داخل معاملة واحدة ثم يحمّل النسخة (فلا يهم أن مخططها الحالي أحدث)، ويطبّق ترحيلات **الصورة المحددة** (لا `latest`)، ويوقف النشر في كل مساحات العمل ويشغّل web فقط. بعدها: راجع الحسابات بحثًا عن منشورات خرجت بعد وقت النسخة، شغّل العامل (`docker compose up -d worker` أو أعد الأمر بـ `--resume`)، واستأنف النشر من **الإعدادات**. البيانات التي دخلت بعد النسخة (حتى 24 ساعة لو كانت اليومية) تضيع؛ لهذا تؤخذ نسخة قبل كل نشر. لا تنشر `main` من جديد قبل إصلاح الإصدار المعطوب، وإلا عاد.

## النسخ الاحتياطي

التفاصيل (الاسترجاع، النقل، rclone) في [00-deploy.md](00-deploy.md#8-النسخ-الاحتياطي-والاسترجاع). باختصار:

```bash
bash backup.sh                                              # نسخة الآن
bash backup.sh status                                       # عمر آخر نسخة ناجحة
ls -lt /srv/repeater/backups | head                              # آخر النسخ
bash backup.sh restore /srv/repeater/backups/<file>.sql.gz --yes
```

فشل النسخة اليومية أو مرور 36 ساعة بلا نسخة ناجحة يصلك على تيليجرام (يلزم [04-telegram.md](04-telegram.md))؛ `repeater.cli check` يعرض أيضًا عمر آخر نسخة (`backups:`)، والصفحة الرئيسية في اللوحة تعرض تحذيرًا لمالك مساحة العمل إن مرّت 36 ساعة أو أكثر على آخر نسخة ناجحة.

## الأسرار والمفاتيح

- تغيير مفاتيح منصة: عدّل `deploy/.env` أو سر GitHub ثم انشر.
- **تدوير مفتاح تشفير التوكنات** (`REPEATER_TOKEN_ENCRYPTION_KEYS`، حلقة مفاتيح كل مفتاح له معرّف فريد `k1` و`k2`...؛ الأول يشفّر الجديد وكلها تفك):
  1. ولّد المفتاح الجديد: `dc exec web python -m repeater.cli gen-secrets`. بما أن الحلقة موجودة في بيئة الحاوية يختار الأمر المعرّف التالي الحر (`k2`) ويطبع **الحلقة الجديدة كاملة**: `REPEATER_TOKEN_ENCRYPTION_KEYS=k2:جديد,k1:قديم` (تحوي مفاتيحك الحالية، فعامِلها كسر). `--kid` يحدد المعرّف، و`--with-secret-key` يطبع معها `REPEATER_SECRET_KEY` جديدًا (تغييره يُخرج كل المستخدمين من الجلسات ويبطل روابط الوسائط الموقّعة الحالية).
  2. ضع السطر في `deploy/.env` (استبدل القيمة القديمة)، وانشر: `bash deploy.sh`. التطبيق يشفّر الجديد بـ `k2` ويفك القديم بـ `k1`.
  3. أعد تغليف كل التوكنات المخزّنة بالمفتاح الجديد: `dc exec web python -m repeater.cli rotate-keys` (`--dry-run` للمعاينة). آمن لإعادة التشغيل، يقفل كل صف أثناء تحديثه فلا يطمس تجديدًا أجراه العامل، ويطبع كم قيمة كانت مغلفة بكل مفتاح قبل وبعد. توكنات ميتا لا تتجدد أبدًا، لذلك لن تنتقل من `k1` بدون هذا الأمر.
  4. لو أبلغ الأمر عن قيم لم يستطع قراءتها (معرّف مفتاح غير موجود في الحلقة) فأرجِع ذلك المفتاح أو أعد ربط تلك الحسابات، ثم أعد الأمر.
  5. حين يقول الأمر إنه لا قيمة تستخدم `k1` احذفه من `.env` وانشر. **لكن** النسخ الاحتياطية المأخوذة قبل التدوير (حتى 14 يومًا محلية و30 بعيدة) تحتفظ بتوكنات مغلفة بـ `k1`: احتفظ بـ `k1` في مدير كلمات المرور حتى تنقضي، فاسترجاعها بدونه يعني إعادة ربط كل الحسابات.
  - **بعد تسرب `.env`:** التدوير وحده لا يكفي. من يملك المفتاح القديم وقاعدة بياناتك (أو نسخة منها) يفك التوكنات القديمة؛ التوكنات نفسها يجب أن تُلغى عند المنصات (فصل الحسابات من اللوحة ثم إعادة ربطها، وتغيير أسرار التطبيقات في تيكتوك وGoogle وميتا).
- لا تغيّر `POSTGRES_PASSWORD` في `.env` وحده: القاعدة الموجودة ستبقى على القديمة.

## استكشاف الأعطال

| العَرَض | السبب المرجّح | الحل |
|---|---|---|
| المتصفح: لا يفتح `rotator.magic-lap.com` | سجل DNS غير موجود أو برتقالي، أو جدار Hostinger يغلق 80/443 | راجع سجل A (DNS only)، ثم `dc logs caddy` |
| خطأ شهادة / Caddy لا يستخرج شهادة | الـ DNS لا يشير للسيرفر بعد، أو المنفذ 80 مغلق | `dig +short rotator.magic-lap.com`، وانتظر انتشار DNS؛ Caddy يعيد المحاولة وحده |
| 502 من Caddy أو البروكسي | حاوية web متوقفة أو غير سليمة | `dc ps` و`dc logs --tail 100 web` |
| 413 عند رفع فيديو | بروكسي Cloudflare مفعّل (حد 100 ميجا) أو حد البروكسي الخارجي | اجعل السجل DNS only؛ في nginx: `client_max_body_size 600m` |
| العامل unhealthy | ملف النبض قديم: العامل عالق أو القاعدة متوقفة | `dc logs --tail 200 worker` ثم `dc restart worker` |
| `Permission denied` على الوسائط | مجلد الوسائط ليس للمستخدم 10001 | `chown -R 10001:10001 /srv/repeater/media` |
| `migrate` يفشل عند النشر | خطأ ترحيل؛ الإصدار القديم يبقى شغالًا | اقرأ الخطأ في سجل النشر وأصلحه ثم انشر مجددًا |
| `password authentication failed` للقاعدة | `POSTGRES_PASSWORD` في `.env` لا يطابق القاعدة | أرجع `.env` من النسخة المحفوظة |
| انستجرام: فشل تنزيل الوسائط | خوادم ميتا لا تصل لرابط `/m/...` | السجل DNS only، و`curl -I` للرابط من خارج السيرفر |
| تيكتوك: `unaudited_client_can_only_post_to_private_accounts` | التطبيق غير مدقق والحساب عام | انشر على حساب خاص حتى التدقيق ([01-tiktok.md](01-tiktok.md)) |
| يوتيوب/Drive يطلب إعادة ربط كل أسبوع | تطبيق Google في وضع Testing (7 أيام) | أعد الربط، أو Internal/Production ([02-google.md](02-google.md)) |
| yt-dlp: `Sign in to confirm you're not a bot` | يوتيوب يحجب عناوين مراكز البيانات | ملف كوكيز للمصدر في `REPEATER_YTDLP_COOKIES_DIR` أو `REPEATER_YTDLP_PROXY`، أو الرفع اليدوي/Drive |
| المنفذ 8090 مستخدم | خدمة أخرى عليه | غيّر `REPEATER_WEB_PORT` في `.env` وفي إعداد البروكسي، ثم `deploy.sh` |
| `bootstrap.sh` يتوقف برسالة `deploy/.env does not fit this host` | `.env` منقول من سيرفر آخر، أو بروكسي آخر يملك 80/443، أو عنوان الربط ليس لهذا السيرفر | اقرأ السطر الذي قبلها؛ لإعادة اختيار الوضع: `sudo bash bootstrap.sh --redetect-proxy` |
| وصلك تنبيه تيليجرام "Repeater backup FAILED" أو "STALE" | القاعدة متوقفة، القرص ممتلئ، rclone فشل (أو تجاوز `RCLONE_MAX_DELETE`)، أو الـ cron متوقف | `journalctl -t repeater-backup --since yesterday` ثم `bash backup.sh` يدويًا |
| بعد الاسترجاع: لا يُنشر شيء | الاسترجاع يوقف النشر في كل مساحات العمل عمدًا | راجع الحسابات ثم استأنف من **الإعدادات** (وشغّل العامل لو لم يعمل) |
| `deploy.sh` يتوقف عند "pre-deploy backup failed" | النسخة قبل النشر فشلت (قرص؟ القاعدة؟) | أصلح السبب؛ أو `SKIP_PREDEPLOY_BACKUP=1 bash deploy.sh` على مسؤوليتك |
| لا تصل تنبيهات تيليجرام | توكن أو chat id خطأ | [04-telegram.md](04-telegram.md) |
